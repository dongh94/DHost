# DHost 분석 정리

원본: `DHost_PRD_v1.0.md` (PRD v1.0 통합 검토본, 2026-11-05)

## 1. 한 줄 요약

**여러 고객사의 Linux 서버를 안전하게 찾아서 접속하고 작업하는 macOS(M2)용 SSH 데스크톱 클라이언트.**
Termius, SecureCRT, Royal TSX 같은 제품군에 속한다. 가장 큰 차이는 **운영 서버 사고 방지(안전)**를 편의보다 앞에 둔다는 점이다.

## 2. 누구의 어떤 문제를 푸는가

| 항목 | 내용 |
|---|---|
| 사용자 | 여러 고객사 서버에 SSH로 들어가 일하는 인프라·운영 엔지니어(본인) |
| 문제 1: 찾기 | 서버가 많고 고객사별로 흩어져 있어 찾고 접속하기 번거롭다 |
| 문제 2: 사고 | 운영 서버에서 잘못 붙여넣거나 엉뚱한 서버에 접속하는 실수가 위험하다 |
| 문제 3: 인증정보 | 비밀번호와 키를 안전하게 보관하면서 서버별로 섞이지 않게 써야 한다 |
| 문제 4: 효율 | 여러 세션을 동시에 쓰고 Jump Host를 거쳐 들어가야 한다 |

## 3. 제품의 핵심 4축

1. **접속 관리**: 고객사 > 폴더 > 서버 구조, 검색, 즐겨찾기, 프로필 CRUD
2. **터미널**: xterm.js 기반 실시간 입출력, ANSI, 한글, vim/top/less, 다중 탭
3. **보안**: 호스트 키 수동 승인, 키 변경 시 차단, 비밀정보 분리 저장, 붙여넣기 경고, 원격 클립보드 차단, 운영 서버 표시
4. **효율**: 다중 독립 세션, 단일 Jump Host, 기존 `~/.ssh/config` 활용

## 4. 문서 전체에 깔린 설계 철학: "사용자가 직접 결정한다"

여러 정책이 같은 원칙에서 나온다. **앱이 사용자 대신 연결하거나 전송하지 않는다.**

- 앱을 실행해도 자동으로 연결하지 않는다 (POL-06, FUN-11)
- 끊기면 사용자가 직접 재접속한다. 자동 재접속은 없다 (FUN-07)
- 처음 보는 호스트 키는 사용자가 승인해야 연결된다 (FUN-04)
- 여러 줄이나 위험한 제어문자를 붙여넣으면 승인 전까지 보내지 않는다 (FUN-08)
- 설정을 복원해도 자동으로 접속하지 않는다
- 백업에는 인증정보를 넣지 않는다 (POL-05)

→ 구현할 때 기능마다 **"이 동작을 사용자가 명시적으로 요청했는가"**를 확인 기준으로 삼으면 된다.

## 5. 확정된 것과 아닌 것

### 확정 (바로 따르면 됨)
- 앱 이름: DHost (과거 이름 CloudTerm)
- 플랫폼: macOS M2 먼저, Windows/Linux는 나중
- UI: 한국어 먼저, 영어는 나중 / 테마는 시스템 연동 + 수동 변경
- 백업·복원: 수동, 인증정보 제외
- 출시 조건: 핵심 기능·보안·안정성 테스트 통과
- 단일 Jump Host는 첫 정식 버전(v1.0)에 포함

### 제안 단계 (승인 필요)
- MVP / v1.0 / v1.x / v2 범위 구분
- 보안 보완안 SEC-P01~P07, 추가 후보 GAP-01~08
- 기술 스택 전체

### 문서의 한계
- STEP 01~07 원문이 없어서 세부 정책을 아직 대조하지 못했다. 원문에 이미 정해진 내용이 있을 수 있다.

## 6. 릴리스 단계 (제안안)

| 단계 | 내용 |
|---|---|
| **MVP** | 서버 관리, SSH 연결(비밀번호/키/Agent/대화형), 호스트 검증, 터미널, 다중 탭, 수동 재접속, 붙여넣기 경고, 로컬 저장, 한국어·테마 |
| **v1.0** | MVP + 단일 Jump Host, ssh config 연동, 오류 진단, 백업·복원, 보안 검증, 배포 |
| v1.x | SFTP, 화면 분할, Local Port Forwarding, 앱 잠금, 터미널 커스터마이징 |
| v2.0+ | 다중 Jump Host, 포트 포워딩 확장, Windows/Linux, OpenStack/K8s 운영 기능 |

## 7. 기술 스택 (초기안)

Tauri 2 + Rust 백엔드 / React + TypeScript + Zustand / Tailwind + shadcn/ui / xterm.js / macOS OpenSSH / SQLite 또는 설정 파일

## 8. 개발 전에 정해야 할 핵심 결정 (분석 의견)

PRD의 미결정 항목 중 **코드 구조에 바로 영향을 주는 것**만 우선순위대로 골랐다.

| 우선순위 | 결정 | 왜 먼저인가 | 의견 |
|---|---|---|---|
| 1 | **SSH 엔진**: 시스템 `ssh` 프로세스(PTY) vs Rust SSH 라이브러리(예: russh) | 호스트 키 승인 UI, 인증 방식, Jump Host, 오류 진단 구현 방식이 전부 달라진다 | PRD는 "macOS OpenSSH"라고 썼다. 이 방식이면 ssh_config와 Agent를 그대로 쓸 수 있다. 대신 지문 승인 UI와 비밀번호 입력을 앱에서 처리하려면 `known_hosts` 분리, `SSH_ASKPASS`, 출력 파싱 같은 우회 작업이 필요하다. 라이브러리 방식은 제어가 쉽지만 ssh_config 해석을 직접 만들어야 한다. **첫 마일스톤 전에 확정 필요** |
| 2 | **비밀정보 저장소** (OPEN-02) | 설정과 비밀정보를 분리한다는 정책의 구현 방식 | macOS Keychain 사용이 자연스럽다 |
| 3 | **로컬 저장 방식** (OPEN-09) | 고객사/폴더/서버 데이터 모델 | 계층 구조, 검색, 즐겨찾기, 이력까지 고려하면 SQLite가 유리하다 |
| 4 | **SSH config 우선순위** (OPEN-01) | v1.0 기능이지만 데이터 모델에 영향을 준다 | 최종 적용값과 출처를 보여주는 방식(SEC-P02) 채택 권장 |
| 5 | 최소 macOS 버전 (OPEN-07) | 빌드 타깃 | 출시 전까지 정하면 된다 |

## 9. 첫 번째 목표 (PRD 10.2 기준)

> MacBook M2에서 앱 실행 → 테스트 Linux VM에 SSH 연결 → 호스트 키 확인·인증 → `hostname`, `whoami`, `uptime` 실행 결과 표시 → 세션 종료 시 자원 정리

이 목표만 달성해도 위 결정 1(SSH 엔진)이 실제로 검증된다.

## 10. SSH 엔진 비교

### 후보
- **A. 시스템 OpenSSH**: Rust가 PTY로 `/usr/bin/ssh`를 실행하고, 그 출력을 xterm.js로 전달한다.
- **B. russh**: 순수 Rust로 만든 async SSH 라이브러리. 앱 안에서 SSH 프로토콜을 직접 처리한다.
- **C. libssh2 (`ssh2` crate)**: C 라이브러리 바인딩. 동기식이고 개발 속도가 느리며 지원 알고리즘이 적어서 제외했다.

### PRD 요구사항별 비교

| 요구사항 | A. 시스템 OpenSSH | B. russh |
|---|---|---|
| 호스트 키 승인 UI (FUN-04) | `KnownHostsCommand`(OpenSSH 8.5+)로 접속할 때마다 앱 helper가 호출되어 지문을 받는다. 이때 UI 승인을 받는다. 키가 바뀌면 ssh가 연결을 차단한다. 경유 서버마다 각각 호출된다 | `check_server_key` 콜백에서 직접 처리한다. 가장 깔끔하다 |
| 비밀번호·대화형 인증 (FUN-03) | `SSH_ASKPASS` + `SSH_ASKPASS_REQUIRE=force`로 앱 입력창에 연결한다. 동작은 하지만 프롬프트 문자열로 맥락을 추측해야 한다 | 인증 단계를 API로 직접 제어한다. 실패 이유가 구조화되어 나온다 |
| SSH Agent | 그대로 사용할 수 있다 (macOS Keychain 연동 포함) | agent 클라이언트를 따로 연결해야 한다 |
| Jump Host (FUN-13) | `-J` / ProxyJump가 기본 지원되고 검증된 기능이다 | direct-tcpip 채널을 열고 그 위에 세션을 다시 만들어야 한다. 직접 구현해야 한다 |
| 기존 ssh_config (FUN-14) | 완벽하게 해석한다. `ssh -G host`로 최종 적용값을 볼 수 있다 (SEC-P02에 딱 맞음) | 해석기를 직접 만들거나 불완전한 crate를 써야 한다. `Include`·`Match` 지원이 약하다 |
| 구형 서버·네트워크 장비 호환 | 매우 넓다 | 오래된 KEX나 암호 알고리즘에서 실패할 수 있다 |
| 오류 진단 (FUN-16) | 종료 코드 255와 stderr를 파싱해야 한다. 덜 구조적이다 | 오류 타입이 명확하다 |
| 세션 정리 (GAP-01) | 앱이 강제 종료되면 자식 ssh 프로세스가 남지 않게 관리해야 한다 | 앱 프로세스 안에서 끝난다 |
| 붙여넣기 경고·클립보드 차단 | 엔진과 무관하다 (xterm.js와 앱 계층에서 처리) | 같음 |
| 향후 SFTP·포트포워딩 | `sftp` 실행 또는 ControlMaster 다중화. 포워딩은 `-L` | russh-sftp, 채널 API로 자유롭게 구현 |
| Windows 확장 | Windows 10 이상에 OpenSSH 내장. 버전 차이에 주의 | 플랫폼과 무관하다 |
| 보안 책임 | 검증된 OpenSSH에 맡긴다 | 프로토콜 구현 신뢰를 라이브러리에 의존한다 |
| 구현량 (MVP~v1.0) | 적다 | 많다 (Jump Host와 ssh_config가 특히 큼) |

### 결론 (권장)

**MVP와 v1.0은 A(시스템 OpenSSH)로 시작하고, 엔진은 Rust trait 뒤로 추상화한다.**

- v1.0에 들어가는 단일 Jump Host, ssh_config, Agent를 OpenSSH가 거의 공짜로 해결해 준다.
- A의 약점이던 호스트 키 승인 UI는 `KnownHostsCommand`로 정석적으로 풀 수 있다. 앱이 known_hosts를 따로 관리하고 `StrictHostKeyChecking=yes`를 함께 쓴다.
- 비밀번호 입력은 askpass helper로 처리한다. 대화형 인증에서 맥락을 추측해야 하는 문제는 남는다.
- 나중에 SFTP나 세밀한 제어가 필요해지면 해당 기능만 B로 교체할 수 있도록 인터페이스를 미리 나눠 둔다.

### 함께 정해야 할 정책
- 사용자의 `~/.ssh/known_hosts`를 같이 읽을지, 앱 전용 known_hosts만 쓸지
- 사용자의 `~/.ssh/config`를 그대로 따를지, 앱 프로필 값을 우선할지 (OPEN-01)
- 지원할 최소 OpenSSH 버전 (KnownHostsCommand는 8.5+, ASKPASS_REQUIRE는 8.4+) → 최소 macOS 버전(OPEN-07)과 함께 결정

### 검증 스파이크 (1~2일)
1. Tauri 앱에서 PTY로 ssh를 실행하고 xterm.js에 연결한다.
2. `KnownHostsCommand` helper로 최초 접속 시 승인 다이얼로그를 띄운다. 키를 바꿨을 때 차단되는지 확인한다.
3. askpass로 비밀번호 인증이 되는지 확인한다.
4. `-J`로 Jump Host를 경유할 때 두 호스트 모두 승인 흐름을 타는지 확인한다.
5. 앱을 강제 종료한 뒤 ssh 프로세스가 남아 있는지 확인한다.
